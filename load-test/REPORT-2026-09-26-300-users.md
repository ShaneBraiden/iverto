# Load Test Report: Test 3 of 3, 300 Concurrent Users

**Date:** 26 Sep 2026, 10:25 – 10:32 IST  
**Target:** `https://api.iverto.ai/devhostel`, Hostel **v2** API (`/v2/tenants/acme/...`)  
**Tool:** k6 v2.2.0, `k6/v2/users.js`, run from one Windows laptop (one public IP)  
**Traffic:** reads only. No passes, decisions or other writes were sent.

## 4. What went wrong

1. **The app is unusable.** A student opening the app waits **82 s (median) to 103 s (p95)** for the home screen's requests to finish. Real users force-close long before that, so the actual failure rate is far higher than the 0.58% HTTP errors suggest.
2. **Throughput is capped at ~30 req/s** and doesn't grow with users: 30 → 100 → 300 users gave 24 → 27 → 30 req/s.
3. **Every staff screen fails 100%.** Dashboard, roster and groups return `500` or time out. Wardens cannot see who is inside or approve anything at this load.
4. **All endpoints queue on one shared bottleneck.** `/app-config` (a constant) has the same ~7 s median as DB-heavy calls. This is the signature of an exhausted DB connection pool (or a single worker) where requests wait for a slot.
5. **Work was left unfinished when the test ended.** 145 journeys were still waiting on the server after the 30 s graceful ramp-down.
6. **Good news:** unlike the 24 Sep arrival-rate test (30 journeys/s, Caddy `502`, 2.5 min recovery), the server **did not crash**. A health check straight after the run answered in 0.4 s. Closed-model users slow down when the server slows down, so the backlog never grew enough to kill the process. A real crowd that retries and reopens the app behaves more like the 24 Sep test.

## 5. Fixes

Same root causes as Tests 1 and 2, now with the full picture. Order matters.

| # | Problem | Fix | Expected effect |
|---|---|---|---|
| 1 | Unknown exact bottleneck | Pull server metrics for 10:25–10:32 IST: DB pool `waiting` count, active connections, Postgres `pg_stat_activity`, CPU, event-loop lag. Confirm pool exhaustion. | Confirms the diagnosis |
| 2 | Staff reports hold connections for 15–30 s | Dashboard: one aggregate query plus a 15–30 s cache. Roster: SQL pagination plus indexes. Groups: remove N+1. `statement_timeout` 5 s. Separate small pool for reports. | Frees the pool; removes all `500`s |
| 3 | Student reads slow at the source (`/me/student` 0.4 s at 30 users) | Indexes `(tenant_id, student_id)`, `(tenant_id, site_id)`, `(tenant_id, status, created_at)`, `(student_id)` on guardian links; remove guardian N+1 in `/me/student` and `/me/children*` | ~5–10× more req/s per connection |
| 4 | Static data hits the DB on every app open | Cache `/app-config`, `/me/branding`, `/sites`, `/categories` (Redis/in-memory + `ETag`/`Cache-Control`) | ~35% fewer DB requests |
| 5 | Unbounded queueing | Pool size 20–30, acquire timeout 1–2 s, fast `503` + `Retry-After` on saturation. App: show "busy, retrying" and back off instead of spinning. | Fails fast instead of 80 s waits |
| 6 | One instance | ≥ 2 app instances behind Caddy with active health checks; scale DB (or add a read replica for reports) | Linear headroom |
| 7 | Verify | Re-run `k6 run -e USERS=300 k6/v2/users.js`. Pass: p95 < 800 ms, errors < 1%, staff endpoints 100% `2xx`, throughput ≥ 100 req/s. | |
