# Load Test Report: Test 2 of 3, 100 Concurrent Users

**Date:** 26 Sep 2026, 10:15 – 10:21 IST  
**Target:** `https://api.iverto.ai/devhostel`, Hostel **v2** API (`/v2/tenants/acme/...`)  
**Tool:** k6 v2.2.0, `k6/v2/users.js`, run from one Windows laptop (one public IP)  
**Traffic:** reads only. No passes, decisions or other writes were sent.

---

## 1. Verdict

**FAIL (latency).** The server did not fail outright. It just got slow for everyone.

| SLO | Target | Result | |
|---|---|---|---|
| HTTP error rate | < 1% | **0.69%** (64 / 9,252) | ✓ |
| Checks passed | > 99% | **99.30%** | ✓ |

| Latency p99 | < 2 s | **8.63 s** | ✗ |

| `GET /dashboard` success | 100% | **2%** (52 of 53 returned `500`) | ✗ |

The error rate stays under 1% only because 97% of traffic is cheap student reads, and they queue rather than fail. **A student opening the app now waits ~28 s** (p50 journey time, including ~5 s of think time) instead of ~9 s.

## 4. What went wrong

1. **Hard throughput ceiling at ~27–30 req/s.** Going from 30 to 100 users added 14% throughput and multiplied latency 9–17×. The backend is fully saturated. Any further users only lengthen the queue.
2. **Every endpoint became slow, including trivial ones.** `/app-config` p50 went 95 ms → 1.8 s, which points to a **shared bottleneck** (DB connection pool, or one Node process whose event loop is waiting on DB callbacks), not one bad query.
3. **Staff screens now fail almost completely.** `/dashboard` 98% `500`, `/groups` 100% `500` (it was 0% errors at 30 users), `/roster` 88% timeouts. The server returns `500` after ~15–22 s, which fits a statement/acquire timeout.
4. **Periodic stalls.** Three windows where throughput fell to 12–18 req/s and p95 went to 8–9 s, each caused by heavy staff queries piling up.
5. **Low error rate hides the problem.** Real users won't wait 28 s. They will force-close and reopen the app, which adds even more requests (retry amplification). This test didn't model that.

## 5. Fixes

| # | Problem | Fix |
|---|---|---|
| 1 | ~30 req/s ceiling, all endpoints queue | Find the saturated resource first: pull server metrics for 10:15–10:21 IST (DB pool wait time, active connections, CPU, event-loop lag). Most likely the Postgres pool (small default size, e.g. 10) held by slow staff queries. |
| 2 | Slow queries holding the pool | `EXPLAIN (ANALYZE, BUFFERS)` on `/dashboard`, `/roster`, `/groups`, `/me/student`, `/sites`, `/me/curfew`. Add composite indexes: `(tenant_id, site_id)`, `(tenant_id, student_id)`, `(tenant_id, status, created_at)` on permissions, `(student_id)` on guardian links, `(group_id)` on group members. |
| 3 | `/dashboard` / `/groups` / `/roster` 98–100% failure | One aggregate query + 15–30 s cache for dashboard. DB-side pagination for roster. Remove N+1 in groups. Target < 300 ms each. |
| 4 | Staff reports starve students | Separate pool (or read replica) for reports. `statement_timeout` ≈ 5 s. |
| 5 | Cheap endpoints wait behind DB | Cache `/app-config`, `/me/branding`, `/sites`, `/categories` in memory or Redis (they change rarely), with `Cache-Control` / `ETag` so the app can skip the call. That removes ~35% of all requests from the DB path. |
| 6 | Queue grows without bound | Explicit pool size (20–30), 1–2 s acquire timeout, return a fast `503` + `Retry-After` when saturated, so the app backs off instead of users retrying on a 30 s spinner. |
| 7 | Single instance | After the query fixes, run ≥ 2 app instances behind Caddy with active health checks. |
