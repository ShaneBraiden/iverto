# Iverto Backend — Load & Stress Test Report

**Date:** 24 Sep 2026, 10:50 – 11:45 IST (main run) · re-run 19:38 – 19:47 IST (§2.7)  
**Target:** `https://api.iverto.ai/devhostel` — Hostel **v2** API (`/v2/tenants/acme/...`) + Socket.IO gateway  
**Tenant:** `acme` (test accounts from `Test/*.csv`: 500 students, 756 guardians, 18 staff)  
**Tool:** k6 v2.2.0, run from one Windows laptop (single public IP)  
**Traffic:** reads only. No passes, decisions, pings or other writes were sent.  
**Scope of this document:** findings and recommended fixes. **Nothing has been fixed.**

---

## 1. Verdict

**FAIL.** In its current state the dev backend would not survive a normal hostel evening rush.

| # | Test | Result | Headline |
|---|---|---|---|
| 1 | Pre-flight (log in every account) | ⚠ **Blocked** | Login is capped at **10 per minute per IP**. 1,274 accounts would take about 2 hours. |

- `POST /v2/auth/password/login`: the 10th login inside ~5 s returned `429 "Too many attempts"` with `Retry-After: 60`. It cleared after ~55 s. **Limit ≈ 10 logins per 60 s**, observed **across different accounts from one IP**.

- `POST /v2/auth/refresh` is in the same `public-auth` rate class in the contract.
- Access tokens expire after **15 minutes**.
- Responses have no `RateLimit-*` headers.
- Reads are **not** throttled: 600 reads at 20/s on one token all returned 200.

## 3. What went wrong, and how to fix it

Ordered by impact. **P0** = blocks release or production use. **P1** = fix before scale. **P2** = housekeeping.

### P0-1 · The shipped app (1.2.2) cannot log in

**What:** `app.json` / `.env` point at `https://api.iverto.ai/devhostel`, and `lib/api/endpoints.ts` keeps `auth.*` on v1, so the app calls `POST /devhostel/v1/mobile/auth/login`. That route returns **404** (`/devhostel/v1/mobile/me` is also 404). The devhostel deployment is v2-only. Every user is stuck on the login screen.

**Evidence:**
```
POST /devhostel/v1/mobile/auth/login        → 404 {"code":"NOT_FOUND", "instance":"/devhostel/v1/mobile/auth/login"}
POST /devhostel/v2/auth/password/login       → 200 (tenantCode "acme", clientType "tenant_mobile")
```

**Fix (pick one):**
1. **Move the app's login to v2**: `POST /v2/auth/password/login` with `{tenantCode, identifier, password, clientType:"tenant_mobile"}`, and refresh via `POST /v2/auth/refresh`. The app needs a tenant-code field (or a hard-coded `acme` for this build).
   Note: v2 does **not** accept roll numbers or phone numbers as `identifier`. Only email worked (`ACM26-0001` → 401). The login screen copy and validation must change too.
2. **Or** deploy the v1 `auth/*` routes on `/devhostel` alongside v2 until the migration is finished.
3. Add a CI smoke check: `curl -f $API_URL/v1/mobile/auth/login` (or `/v2/...`) against the base URL baked into each build **before** it is signed.

### P0-2 · Realtime (Socket.IO) rejects v2 sessions: no live updates

**What:** The `/mobile` namespace auth middleware still validates **v1** tokens. v2 tokens are opaque strings (`beRCaFe3...`, not JWTs), and every one gets `Authentication failed`. Live pass status, warden queues and notifications will never push.

**Fix:**
- Update the socket gateway's `auth` handler to validate v2 sessions (the same session lookup `/v2/auth/session` uses: token → session → principal/tenant).
- Or add a short-lived socket-ticket endpoint (e.g. `POST /v2/realtime/ticket`) and have the app send that ticket in `auth: { token }`.
- Add a test that connects with a fresh v2 token and expects a `40/mobile` ack.

### P0-3 · Backend throughput ceiling ≈ 30 req/s, collapse and slow recovery

**What:** Mixed traffic saturates at 30–35 req/s. Past that, requests queue for 30 s, then Caddy returns `502`, and the service took ~2.5 min to recover after load stopped. A 500–2,000-student hostel opening the app before curfew easily exceeds this.

**Why (evidence, not a guess):**
- `/app-config` alone does **~194 req/s** at p95 316 ms, so Caddy, TLS, networking and Node's event loop are fine.
- DB-backed endpoints plateau much lower (`/me/student` ~14 req/s). Heavy staff queries hold connections for 4–12 s.
- 8 concurrent `/dashboard` calls → all `500` at ~12 s while cheap endpoints stay fast.

→ **Database-bound: slow queries plus connection-pool exhaustion.** Everything queues behind a few heavy queries. The `502` phase means the upstream process died or was restarted (OOM or failed health check) under the queued backlog.

**Fix, in order:**
1. **Pull the server logs and metrics for 11:05–11:16 IST** (use the `requestId`s in the 500 bodies, e.g. `01a0d201-3422-760b-a72d-c6368ee545b4`). Confirm the pool-timeout / statement-timeout error, and check container restarts and memory (OOM kill).
2. **Profile the slow queries** with `EXPLAIN (ANALYZE, BUFFERS)` for `/dashboard`, `/roster`, `/groups`, `/me/student`, `/me/branding`, `/sites`. At 500 students these should be < 50 ms. Seconds means sequential scans or N+1 queries. Likely missing composite indexes: `(tenant_id, site_id)`, `(tenant_id, student_id)`, `(tenant_id, status, created_at)` on permissions, `(student_id)` on guardian links, `(group_id)` on group members.
3. **Remove N+1s**: `/me/student` embeds guardians, so fetch them with one join or `IN (...)` query, not one per guardian. Do the same for groups → members and the roster.
4. **Cache the dashboard**: compute counts with one aggregate query, or keep them in Redis / a materialized view refreshed every 15–30 s. It doesn't need to be real-time per request.
5. **Size and guard the pool**: set an explicit pool size (e.g. 20–30, below Postgres `max_connections`), a short acquire timeout (1–2 s), and a `statement_timeout` (~5 s). A saturated server should return a **fast `503` + `Retry-After`** rather than queue for 30 s.
6. **Give heavy staff reports their own small pool** (or a read replica) so a warden refreshing the dashboard can't starve students.
7. **Scale out** once the queries are fixed: run ≥ 2 app instances behind Caddy with `health_uri` active health checks and `lb_try_duration`, so one crashing instance doesn't mean `502` for everyone.
8. **Re-run `k6/v2/stress.js`** after each change. Target: a knee above 30 journeys/s (≈ 300 req/s).

### P0-4 · `/dashboard` fails at 8 concurrent users, and its numbers don't add up

**What:** One call takes 4.2 s. Eight at once all return `500 INTERNAL_ERROR` at ~12 s. During the stress run, 85% of dashboard calls failed. Wardens and admins would see an error screen whenever a few of them open it together.

The payload is also inconsistent. `studentsInside.total` is 479 for the warden and 485 for the admin, while `inside 456 + outside 44 = 500`.

**Evening update (§2.7):** it is now worse. Single-user `/dashboard` is 5.5 s and `/roster` 9.1 s. At only 2 journeys/s of mixed traffic, 39% of `/dashboard` calls and the only `/roster` call returned `500` at 12–17 s.

**Fix:** as in P0-3 (single aggregate query plus a cache). Concretely:
1. Run `EXPLAIN (ANALYZE, BUFFERS)` on the queries behind `/dashboard` and `/roster` first, since these two alone cause every 500 at low load.
2. Replace the per-request dashboard computation with one `GROUP BY` aggregate over the tenant/site, cached for 15–30 s (Redis or a materialized view). Target < 100 ms.
3. Paginate `/roster` in the database (`LIMIT/OFFSET` or keyset on an indexed column) instead of building the full list and slicing it. Add the `(tenant_id, site_id)` and student-status indexes it filters on. Target < 300 ms for `limit=20`.
4. Set a `statement_timeout` (~5 s) so a slow report returns a fast, retryable `503` instead of holding a pool connection for 15 s and starving other staff calls.

Also fix the counting logic so `total == inside + outside + unknown` for the same scope, and add a unit test asserting that invariant.

### P1-5 · Login and refresh rate limit: 10/min per IP will lock out whole hostels

**What:** All students on hostel Wi-Fi share one public IP (NAT). With a 10/min per-IP limit on login **and** refresh (same `public-auth` class) and **15-minute access tokens**:

- 500 students each refresh 4× an hour ≈ **33 refreshes/min** from one IP, over 3× the limit. Refreshes get `429`, the app treats that as a failed session, and users get logged out.
- After an app update or at the start of term, 500 logins from one IP take **50 minutes** to get through.
- Test tooling hits the same wall: verifying all 1,274 test accounts would take ~2 hours.

(I could only observe this from one IP. If the limit is **global** rather than per IP, the impact is even worse. Check the limiter config.)

**Fix:**
- Key **login** limits on *account + IP* (e.g. 5 failures per account per 15 min), not on IP alone.
- Move **refresh** out of `public-auth`, or give it a separate, far higher limit keyed on the refresh-token family.
- Allowlist known campus egress IPs, or raise the per-IP ceiling to thousands per minute for them.
- Send `RateLimit-Limit` / `RateLimit-Remaining` / `RateLimit-Reset` headers. In the app, treat `429` on refresh as "retry after N s", **never** as "log out".
- Consider a longer access-token TTL for mobile (e.g. 60 min) to cut refresh volume 4×.

### P1-6 · Security: staff MFA is not enforced on MFA-level-1 routes

**What:** All staff logins (admins, wardens, security) return `mfaEnrollmentRequired: true`. The contract (`hostel-v2.bundle.yaml`) marks `/roster`, `/roles` and `/permissions` as `x-mfa-level: 1`. Yet those un-enrolled sessions got **200** with the full student roster (names, rooms, phones), role list and permission queue.

**Fix:** enforce `x-mfa-level` in the backend authorisation middleware: session `mfaLevel` must be ≥ the operation's required level, otherwise `403` with a problem type the app can route to enrollment. Until the app has an MFA enrollment screen, staff will then be locked out. Plan that app work alongside this fix.

**Caveats**
- The generator was one laptop on one IP. The sweep proved it could push ~200 req/s, so the ~30 req/s ceiling belongs to the server, not the generator. The `dropped_iterations` in the load test come from VUs stuck behind the slow server.
- Because tokens were shared, per-account caching effects are slightly flattered. Real traffic from distinct users would be heavier on the DB, not lighter.
- Reads only. Write paths (submit, decisions, late entries) are untested and add DB load on top of this.
- Only 6 of 1,274 accounts were fully verified in pre-flight (rate limit). Of the accounts touched during the session, the failures were `acm0001` and `parent.acm0001` (§P1-7).

## 6. Suggested order of work

1. P0-1 app login → v2 (or deploy v1 auth on devhostel). **Without this, nothing else matters to users.**
2. P0-2 socket auth for v2 tokens.
3. P0-3 / P0-4: server logs → query profiling → indexes / N+1 / dashboard cache → pool + timeouts → second instance.
4. P1-5 rate-limit keys and refresh class.
5. P1-6 MFA enforcement (together with an app enrollment screen).
6. Clean test data (P1-7), then re-run smoke → load → stress. Pass criteria: p95 < 800 ms, errors < 1% at 30 journeys/s, socket connect failure < 5% at 400 connections.
